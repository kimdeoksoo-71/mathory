# Mathory 공유·협업 기능 로드맵

> **문서 목적:** 수학 컨텐츠의 공유, 협업 편집, 피드백 교환, 공개 게시까지의 전체 그림을 정리하고, 간단한 것부터 차례로 구현할 수 있도록 단계별 로드맵을 제시한다.
>
> **원칙:** 당장 유용한 간단한 기능부터 만들고, 필요한 기능을 차차 추가한다.

------

## 1부. 전제 조건 — 지금 반드시 결정·준비해야 할 것들

공유·협업 기능은 현재 Mathory의 단일 사용자 구조 위에 바로 올릴 수 없다. 아래 항목들은 어떤 공유 기능을 만들든 먼저 갖춰져야 하는 기반이다.

### 1.1 데이터 소유권 (owner_uid)

**현재 상태:** `problems` 문서에 소유자 필드가 없다. 누가 만든 문항인지 Firestore 수준에서 구분할 수 없다.

**필요 조치:**

- `problems` 문서에 `owner_uid: string` 필드 추가
- 기존 문항에 일괄로 덕수의 uid를 채워 넣는 마이그레이션 스크립트 작성
- 모든 CRUD 함수에서 `owner_uid`를 자동 설정하도록 수정

**결정 필요:**

- (a) `owner_uid`만 넣을 것인가, 아니면 향후 그룹/팀 개념을 고려하여 `owner_type: 'user' | 'team'` + `owner_id` 구조로 갈 것인가?
- → **권장:** 지금은 `owner_uid`만 추가한다. 팀 개념은 실제로 필요해질 때 확장한다.

### 1.2 Firestore Security Rules 강화

**현재 상태:** Security Rules가 사용자 기반 접근 제어를 하지 않는 것으로 추정된다.

**필요 조치:**

- 기본 규칙: 인증된 사용자만 자기 문항(`owner_uid == request.auth.uid`)을 읽기/쓰기 가능
- 공유 문항에 대한 읽기 허용 규칙 (이후 단계에서 점진적 확장)
- subcollection(question_blocks, solution_blocks, 동적 탭 subcollection)에도 부모 문서의 소유권/공유 상태를 기준으로 규칙 적용

### 1.3 사용자 프로필 컬렉션

**현재 상태:** Firebase Auth에 Google 계정 정보만 있고, Mathory 자체의 사용자 프로필 컬렉션이 없다.

**필요 조치:**

- `users/{uid}` 컬렉션 생성
- 필드: `displayName`, `email`, `photoURL`, `createdAt`
- 최초 로그인 시 자동 생성 (Auth trigger 또는 클라이언트 로직)

**이유:** 공유 시 "누구에게" 공유하는지, 댓글 작성자가 누구인지 표시하려면 사용자 정보가 필요하다.

### 1.4 핵심 설계 결정 사항

아래 질문들은 구현을 시작하기 전에 방향을 정해야 한다.

| #    | 결정 사항      | 선택지                                                       | 권장                                                      |
| ---- | -------------- | ------------------------------------------------------------ | --------------------------------------------------------- |
| D1   | 공유 단위      | 문항(problem) 단위 vs 폴더 단위 vs 둘 다                     | 문항 단위로 시작, 폴더 공유는 나중에 추가                 |
| D2   | 공유 링크 구조 | `/shared/{shareId}` (별도 페이지) vs `/problems/{id}?token=xxx` | 별도 `/shared/{shareId}` 페이지 권장 (에디터와 뷰어 분리) |
| D3   | 공개 범위 모델 | `private` / `link` / `public` 3단계                          | 3단계 모델 채택                                           |
| D4   | 협업 편집 방식 | 실시간 동시 편집 (CRDT/OT) vs 턴 기반 (잠금) vs 제안/승인    | 제안/승인 모드로 시작 (비용·복잡도 최소)                  |
| D5   | 버전 관리 방식 | 수동 스냅샷 vs 자동 저장 이력 vs 둘 다                       | 자동 저장 이력 + 수동 스냅샷 병행                         |
| D6   | 댓글 위치 지정 | 블록 단위 vs 텍스트 범위(인라인)                             | 블록 단위로 시작                                          |

| 0-2  | `users` 컬렉션 생성      | 사용자 프로필 저장소 + 최초 로그인 시 자동 생성 로직       |
| 0-3  | Security Rules 기본 강화 | 소유자만 자기 문항 접근 가능하도록 규칙 설정               |

### Stage 1: 읽기 전용 공유 링크

> 예상 난이도: ★★☆ | 가장 즉시 유용한 기능 — "이 문제 한번 봐봐" 를 링크 하나로 해결

| #    | 기능             | 설명                                                         |
| ---- | ---------------- | ------------------------------------------------------------ |
| 1-1  | 공유 링크 생성   | 문항 편집 화면에 "공유" 버튼 추가. 클릭하면 고유 shareId 생성하여 `shares/{shareId}` 문서에 저장 |
| 1-2  | 공유 뷰어 페이지 | `/shared/{shareId}` 경로의 읽기 전용 페이지. 기존 EditorPreview 컴포넌트를 재활용하되 편집 UI 제거 |
| 1-3  | 링크 복사 UI     | 공유 링크를 클립보드에 복사하는 버튼 + 토스트 알림           |
| 1-4  | 공유 해제        | 공유 링크를 비활성화(삭제)하는 기능                          |

**Firestore 구조:**

```
shares/{shareId}
  ├─ problemId: string
  ├─ owner_uid: string
  ├─ visibility: 'link' | 'public'
  ├─ created_at: timestamp
  └─ expires_at?: timestamp (선택적 만료일)
```

**Security Rules:** `shares` 문서의 `visibility`가 `'link'`이면 shareId를 아는 누구나 해당 problem을 읽기 가능.

### Stage 4: 편집 제안 (Suggestion Mode)

> 예상 난이도: ★★★★☆ | Google Docs의 "제안 모드"와 유사 — 실시간 동시 편집 없이 협업 가능

| #    | 기능             | 설명                                                         |
| ---- | ---------------- | ------------------------------------------------------------ |
| 4-1  | 편집 제안 생성   | `editor` 역할의 사용자가 수정한 내용을 원본에 바로 반영하지 않고, 제안(suggestion)으로 저장 |
| 4-2  | 제안 데이터 모델 | `problems/{id}/suggestions/{sugId}`: `{blockId, original_text, suggested_text, author_uid, status: 'pending' |

## 3부. 구현 순서 요약

아래는 권장 구현 순서이다. 각 Stage는 이전 Stage의 완료를 전제한다.

```
Stage 0  ─→  Stage 1  ─→  Stage 2  ─→  Stage 3
(기반)        (링크 공유)   (지정 공유)    (댓글)
                                            │
                              ┌─────────────┼─────────────┐
                              ▼             ▼             ▼
                          Stage 4       Stage 5       Stage 6
                          (편집 제안)    (버전 이력)    (공개 게시)
                              │             │
                              └──────┬──────┘
                                     ▼
                                 Stage 7
                              (실시간 협업)
```

**Stage 3 이후의 Stage 4, 5, 6은 서로 독립적**이므로 필요에 따라 순서를 바꾸거나 병행할 수 있다. Stage 7은 모든 기능이 안정화된 후 착수를 권장한다.

## 5부. Firestore 스키마 확장 요약

현재 스키마에 추가되는 컬렉션/필드의 전체 그림이다.

```
users/{uid}                          ← Stage 0 (신규)
  ├─ displayName: string
  ├─ email: string
  ├─ photoURL: string
  └─ createdAt: timestamp

problems/{problemId}                 ← Stage 0 (기존 문서에 필드 추가)
  ├─ owner_uid: string               ← 추가
  ├─ visibility: 'private'|'link'|'public'  ← 추가
  ├─ (기존 필드들 유지)
  ├─ question_blocks/{blockId}       (기존)
  ├─ solution_blocks/{blockId}       (기존)
  ├─ {dynamicTab}_blocks/{blockId}   (기존, Phase 21)
  ├─ comments/{commentId}            ← Stage 3 (신규)
  │   ├─ blockId: string
  │   ├─ author_uid: string
  │   ├─ content: string
  │   ├─ parentCommentId?: string
  │   ├─ resolved: boolean
  │   └─ created_at: timestamp
  ├─ suggestions/{sugId}             ← Stage 4 (신규)
  │   ├─ blockId: string
  │   ├─ original_text: string
  │   ├─ suggested_text: string
  │   ├─ author_uid: string
  │   ├─ status: 'pending'|'accepted'|'rejected'
  │   └─ created_at: timestamp
  └─ versions/{versionId}            ← Stage 5 (신규)
      ├─ snapshot: object             (전체 블록 상태의 직렬화)
      ├─ author_uid: string
      ├─ label?: string              (수동 스냅샷 이름)
      ├─ auto: boolean               (자동 vs 수동)
      └─ created_at: timestamp

shares/{shareId}                     ← Stage 1 (신규)
  ├─ problemId: string
  ├─ owner_uid: string
  ├─ visibility: 'link' | 'public'
  ├─ created_at: timestamp
  ├─ expires_at?: timestamp
  └─ members/{uid}                   ← Stage 2 (신규)
      ├─ role: 'viewer'|'commenter'|'editor'
      └─ addedAt: timestamp

notifications/{notifId}              ← Stage 3 (신규)
  ├─ recipient_uid: string
  ├─ type: 'comment'|'suggestion'|'share_invite'|...
  ├─ source_problem_id: string
  ├─ actor_uid: string
  ├─ read: boolean
  └─ created_at: timestamp
```

## 6부. 각 Stage별 예상 작업량

| Stage              | 핵심 작업                                | 예상 규모     | 즉시 사용 가치                                    |
| ------------------ | ---------------------------------------- | ------------- | ------------------------------------------------- |
| **0: 기반**        | 필드 추가, 마이그레이션, Rules           | 소 (1~2일)    | 없음 (인프라)                                     |
| **1: 링크 공유**   | shares 컬렉션, 뷰어 페이지, 링크 복사 UI | 소~중 (2~3일) | **높음** — 즉시 다른 사람에게 문항 보여줄 수 있음 |
| **2: 지정 공유**   | 사용자 검색, 역할 시스템, 공유받은 목록  | 중 (3~5일)    | 중간 — 특정인에게만 공유                          |
| **3: 댓글**        | 댓글 CRUD, UI, 수식 지원, 알림           | 중 (4~6일)    | **높음** — 피드백 교환의 핵심                     |
| **4: 편집 제안**   | 제안 데이터 모델, Diff 표시, 승인/거절   | 대 (5~8일)    | 중간 — 협업 편집의 안전한 방식                    |
| **5: 버전 이력**   | 스냅샷 저장, 타임라인 UI, 복원, Diff     | 중~대 (4~7일) | 중간 — 이력 관리                                  |
| **6: 공개 게시**   | public 모드, 갤러리, SEO                 | 중 (3~5일)    | 높음 — 컨텐츠 공개 배포                           |
| **7: 실시간 협업** | CRDT/OT 통합, 커서 공유                  | 대 (2~4주)    | 낮음 (당장 불필요)                                |
