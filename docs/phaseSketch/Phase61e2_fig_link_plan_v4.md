## 1. 체크리스트 수행 결과

### V1. ⚠ **D31·C8-①의 전제 반증 — alt는 이미 보호된다** (체크리스트 ⑥에서 발견)

v3 §4: *"현행 보호 목록(`proofread.ts:341`·`:402`)은 `https?://\S+`로 URL만 지킨다. alt는 무방비라 `연구실모의6회…`의 `6`·`260824`가 `$…$`로 감싸인다."*

**실측 — 틀렸다.** 인용한 줄의 **바로 다음 줄**이 마크다운 링크/이미지 **전체(alt 포함)**를 보호한다:

```ts
// lib/proofread.ts:342 (autoWrapBareNumbers) · :403 (autoWrapBareLetters) — 61e 이전부터 존재
addAll(/!?\[[^\]\n]*\]\([^)\n]*\)/g);          // 마크다운 링크/이미지
```

실행 프로브(HEAD `466d347` 단독 컴파일):

```
IN : 그림과 같다. ![연구실모의6회(260824)_문제_1공통07_fig1.jpg](https://drive.google.com/…) 이때 f(1)은?
OUT: …![연구실모의6회(260824)_문제_1공통07_fig1.jpg](…) 이때 $f$(1)은?      ← alt 무변경, count=1 (밖의 f만)
IN : ① ![a_fig1.jpg](https://drive.google.com/file/d/1x/view)\n② 2개
OUT: ① ![a_fig1.jpg](…)\n② $2$개                                        ← alt 무변경, count=1 (2개만)
```

v3가 스스로 N-1에서 경고한 함정(이 파일은 비ASCII 때문에 맨 grep이 매치를 감춘다 — `grep -a` 필요)에 정확히 걸린 것으로 보인다. 귀결:

- **D31 철회** — `lib/proofread.ts` 코드 변경 0. 기존 패턴(`!?…`, URL에 공백 아닌 `[^)\n]*`)이 v3가 제안한 한 줄보다 오히려 넓다. **`test:proofread`의 +2 회귀 케이스만 추가**해 이 행동을 고정한다(현행 코드로 즉시 통과해야 하며, 통과 자체가 V1의 재검증이 된다).
- **C8-① 강등** — 주장된 고장 모드("alt 안 숫자 수식화")는 발생하지 않는다. choices 가드를 새 형식으로 넓히는 것은 결함 수정이 아니라 **기존 `\includegraphics` 가드와의 대칭성**(D3′ "손댈 이유 없는 블록은 손대지 않는다") 문제다. 넓혀도 무해하므로 **채택은 유지하되 근거를 그렇게 고쳐 적는다** — 훗날 이 가드를 지우려는 사람이 "수식화 방지용"이라는 거짓 근거에 묶이면 안 된다.
- **C8-②③(선택지·O열 경고의 이중 형식 탐지)은 유효** — 경고는 "사람이 손봐야 한다"는 신호라 두 형식을 다 봐야 한다. 유지.
- **C11 재정정** — materializeImage 주석의 "D15 덕" 과장 지적은 맞다(리터럴은 autoFix 이후 삽입). 다만 v3의 대체 서술("보호가 일하는 자리는 O열·choices")도 절반만 맞다: 구형 `\includegraphics` 리터럴은 **D15(제어열 보호)**가, 새 형식은 **:342/:403(마크다운 보호)**가 지킨다. 주석은 이 둘을 나눠 적을 것.

### V2. C4 재현 — **확정, 이번 계보 최대 기여** (체크리스트 ①)

```
FIG_NAME_RE.test('연구실모의6회(260824)_문제_1공통07_fig1.jpg'.normalize('NFC')) → true
                                                  …normalize('NFD')            → false
```
NFD 한글은 U+1100 자모 계열이라 `[가-힣ㄱ-ㅎㅏ-ㅣ]`에 안 걸린다 — v2의 D22(이중 검색)만으로는 게이트에서 400으로 죽어 효과 0이라는 v3 판정 그대로다. **§5-3 사양(정규화 → 게이트 → NFC→NFD 순차 검색) 승인.** 61e부터 잠복해 있던 버그라는 서술도 맞다.

### V3. N1·N2 확인 — 단 한 가지 정밀화 (체크리스트 ②)

패치 11의 alt = `nfc_()` (`Datalatex_To_Data_DS.gs:184-191`), 그림 파일 생성은 `stemOf_` 원형(`Mathpix 그림 추출.gs:85, 229`) — **둘 다 확인**. 정밀화 하나: `링크&파일명 추출(키워드).gs:68`이 09-03부터 A열 파일명 자체를 `nfc_(f.getName())`로 기록하므로, **이후 새로 추출되는 그림 파일명은 stem부터 NFC다.** NFD 불일치는 주로 **09-03 이전에 만들어진 파일**(연구실모의6회 등 — macOS에서 올린 원본이 NFD일 때)에서 온다. O3(정규형 실태 실측)의 기대치: "NFD가 나오면 61e부터 조용히 실패하던 그림"이라는 v3 문장에 "그리고 대부분 09-03 이전 생성분일 것"을 더한다. 사양 영향 0 — D29의 이중 검색이 양쪽을 다 덮는다.

### V4. 경미한 빈틈 — 공백 낀 Drive 링크의 침묵 갈래 (체크리스트 ⑤·⑦ 부속)

`FIG_SCAN_RE`의 링크 갈래는 `\(` 직후 공백을 허용하지 않고(61e의 `MATHPIX_IMG_RE`는 `\(\s*` 허용이었다), `FOREIGN_IMG_RE`는 공백 뒤 drive URL을 lookahead로 배제한다. 그래서 `]( https://drive.google.com/…)`처럼 **괄호 안 공백이 낀 Drive 링크는 분할도 경고도 없이 침묵**한다. GAS가 이런 문자열을 만들지 않으므로 실해는 없다 — 링크 갈래에 `[ \t]*`를 넣어 닫거나, 현행 유지 시 §5-1에 "알고 두는 손실" 한 줄로 기록할 것(권장: 전자 — 한 글자 비용).

### V5. 나머지 전건 승인 (체크리스트 ③④⑤⑥⑦)

- **D30(폴백 리터럴 유지, v2 D23 철회)** — 승인. `origText` 복원 = 깨진 `<img>` = 고치려는 증상의 재현이라는 논리, `FigurePreview`(:740·:754)의 "저장본과 같은 모습" 약속, 비공개 Drive URL이 공개 공유·Bazaar로 흘러가는 위험 — 셋 다 실물로 확인했다. v2의 D23은 web이 낸 결정이지만 철회가 옳다.
- **D29(이름만 조회, id 폴백 금지)** — `saveBlob_`의 휴지통 재생성(N5) 확인. 승인.
- **D32(`FIG_NAME_RE` 이주)** — import 방향(route→lib) 확인, import 0 규약 무저촉. 승인.
- **D33·D34·D35** — `f.getUrl()` 반환 형태·GAS `reLink` 호스트·`IMAGE_MIME_OK` 전부 대조 일치. 승인.
- **체크리스트 ⑥(그 자리가 다인가)** — `grep -a` 전수: `includegraphics`를 보는 코드는 sheetImport(:187 스캔·:231 복구), 모달(:104 가드·:167 폴백·:754 프리뷰), proofread(주석뿐). v3의 "다섯 자리" 목록과 일치, 렌더 5곳·전처리 영향 없음 판단도 맞다.
- U 계열·C1~C6·C9·C10, D27(+N8 안내문)·D28 — 이의 없음. C1(CLI가 GAS를 읽을 수 있다)은 관례 기록을 고친다: **이후 GAS 사실도 CLI가 교차검증한다.**

## 3. 교훈 (계보 기록용)

61e Z2(낡은 로컬 사본)와 정확히 대칭인 사고가 났다: 이번에는 원천은 맞았는데 **한 줄 아래를 못 읽었다**. `lib/proofread.ts`는 비ASCII 문자열 때문에 맨 grep이 매치를 감추는 파일이고, 그 함정을 문서화한 당사자(v3 N-1)가 걸렸다. 규약 한 줄 추가: **"무방비다"라는 주장은 반드시 실행 프로브로 재현해서 적는다 — 보호 목록류(protected ranges, 화이트리스트)는 인용이 아니라 실행으로 검증한다.** (C2·C4·V1 세 건 모두 실행 프로브가 판정을 갈랐다.)
