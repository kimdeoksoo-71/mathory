### 0-1. key 마커 의미 모델 (합의된 최종 형태)

| 마커 | 단위 | 문법 | 용도 |
|---|---|---|---|
| **인라인 key** | 문장/구 (한 블록·한 문단 내) | `**...**` (기존 markdown strong) | 텍스트 문장, 인라인 수식 포함 문장 |
| **블록 key** | 블록 전체 | callout(강조문) 블록 | 행 단위 강조 — 특히 **display 수식이던 행** |

**display 수식 행의 강조 관행(덕수 확정)**: 기존 `$$...$$`로 쓰던 행을 강조하고 싶으면 그 행을 **callout 블록으로 옮기고 인라인 수식 `$...$`로 쓴다.** 근거: (a) `**`는 인라인 문법이라 display 블록을 감쌀 수 없고 이는 callout 안에서도 동일하다 — 그래서 블록 강조는 블록 타입 자체가 담당한다. (b) Mathory는 인라인 수식에 `\displaystyle`을 자동 주입(preprocessMath)하므로 `$...$`로도 display급 조판이 나온다. (c) Phase 57 설계상 callout의 `padding-left`(화면 3em/인쇄 2em)가 katex-display 들여쓰기와 일치하고 행 끝 `\tag{n}` tag-marker 파이프라인도 이미 동작 — 수식 행을 callout으로 옮겨도 x좌표·참조번호가 나란히 유지된다.

이 관행의 알려진 한계 1건: `$$ A \\ B $$`처럼 **최상위 `\\`로 여러 행을 나눈 복합 display 수식**은 인라인 `$...$` 하나로 옮길 수 없다(KaTeX 인라인 모드는 최상위 줄바꿈 미지원). 대응: callout 안에서 **한 줄에 하나씩 `$...$`로 나눠 쓴다**(callout은 여러 줄 텍스트 블록이므로 가능). `\begin{cases}` 같은 내부 다행 구조는 인라인에서도 렌더되므로 문제없음. 사용 가이드로 문서화(§6).

## 2. 구현 상세

### 2-1. P1 — 제목 블록 (CSS)

현행: heading 블록이 markdown `##` → `h2`로 렌더되며 글자가 크고 언더라인(border-bottom) 존재. **현행 셀렉터 위치·값은 CLI 실측**(globals.css 또는 EditorPreview inline style로 추정).

```css
/* 화면 — .preview-content 스코프 (셀렉터 좌표는 CLI 실측 후 확정) */
.preview-content h2 {
  font-size: 1.08em;          /* D1: 본문 한 단계 위 */
  font-weight: 700;
  border-bottom: none;        /* D1: 언더라인 제거 */
  padding-bottom: 0;
  margin: 2.4em 0 0.6em;      /* D2: 비대칭 */
  letter-spacing: -0.01em;
}
```

**⚠ 블록 래퍼 마진 비상쇄 문제(핵심 검증 항목)**: Phase 57 v1이 지적했듯 블록 래퍼 div끼리는 마진 상쇄가 일어나지 않을 수 있다. heading이 독립 블록이면 실제 시각 간격 = `블록 간 기존 간격 + h2 margin`이 되어 2.4em이 과대해질 수 있다. CLI는 (a) heading 블록의 래퍼 구조, (b) 블록 간 기존 간격을 실측하고, **"체감 간격 위 2.4em / 아래 0.6em"이 나오도록 마진 값을 역산**할 것 — Phase 57 K1과 같은 "체감 간격으로 정의, 마진은 역산" 방법론.

- 문서 첫 제목 예외: 컨테이너 `:first-child`(또는 블록 index 0) 기준 margin-top 축소. 블록 구조상 CSS만으로 안 되면 렌더 사이트에서 첫 블록 클래스 부여.
- `h3` 이하가 콘텐츠에서 실사용 중인지 CLI 확인 — 사용 중이면 동일 원칙(한 단계씩만 차등)으로 함께 조정.
- 인쇄(PrintStyles.css)의 h2도 동일 원칙 적용(pt 환산). 현행 인쇄 h2 스타일 실측 후 결정.
- 글꼴 크기 슬라이더: 전부 em — 자동 동행.

### 2-2. P2 — 톤 시스템 (CSS + 스코프 클래스)

렌더 사이트 5곳(EditorView 미리보기 / ProblemView / FolderView / ProblemTabContent / PrintableContent)에서 **풀이 블록 컨테이너**에 스코프 클래스를 부여한다:

```
solution 컨테이너: class="solution-tone" + (key 마커 존재 시) "has-key"
question 컨테이너: 무클래스 (불변)
```

```css
/* globals.css */
:root {
  --tone-dim: #6b6a65;   /* 실배경 대비 4.5:1 이상으로 실측 확정 (D3) */
}

/* 톤 낮추기는 has-key일 때만 발동 (D4 폴백) */
.solution-tone.has-key { color: var(--tone-dim); }

/* key 복귀 — KaTeX는 color 상속이므로 수식까지 자동 */
.solution-tone.has-key strong { color: var(--tone-full, inherit); }
.solution-tone.has-key .callout-block { color: var(--tone-full, inherit); }

/* 제목은 톤 대상 제외 (D9) */
.solution-tone.has-key h1,
.solution-tone.has-key h2,
.solution-tone.has-key h3 { color: var(--tone-full, inherit); }

/* D5 — 화면에서 굵기 배제 (가짜 볼드 차단) */
.solution-tone strong { font-weight: inherit; }
```

- `--tone-full`은 현행 본문색을 변수화(현행 값 CLI 실측). 하드코딩 금지 — 다크모드 등 후속 대비.
- **`.has-key`가 없으면 어떤 규칙도 발동하지 않는다** — 기존 문서 시각 변화 0 (D4).
- `strong { font-weight: inherit }`는 has-key 여부와 무관하게 스코프 전체 적용할지, has-key 시에만 적용할지: **v1 제안은 has-key 시에만** — 마커 없는 기존 문서에서 `**`가 여전히 평범한 볼드로 보이도록(변화 0 원칙 우선). CLI 이견 있으면 v2에서.
- 주의: BORDERED 블록 테두리·tag-marker·marker-circled·num-circle은 `currentColor`/상속 여부에 따라 함께 흐려질 수 있다 — **의도된 동작으로 승인**(routine 요소이므로). 단 실렌더에서 흉하게 보이는 요소가 있으면 CLI가 목록화하여 v2에서 개별 판정.
- 콘텐츠 내 `\textcolor` 등 명시 색은 상속을 이기므로 그대로 유지됨 — 문제없음, 기재만.

### 2-3. has-key 판정 로직

컨테이너 단위(풀이 블록 배열 전체) 1회 계산:

```ts
// lib/keyTone.ts (신규, 5개 렌더 사이트 공유)
const KEY_STRONG_RE = /\*\*(?=\S)[\s\S]*?(?<=\S)\*\*/;   // CommonMark 유효 강조 근사
export function solutionHasKey(blocks: Block[]): boolean {
  return blocks.some(
    (b) => b.type === 'callout' || (isTextBased(b.type) && KEY_STRONG_RE.test(b.raw_text))
  );
}
```

- 판정 스코프가 **블록이 아니라 풀이 전체**인 이유: 블록 3에만 key가 있어도 블록 1~5 전체가 흐려져야 대비가 성립한다.
- 정규식은 근사면 충분(오탐 시 최악이 "톤 시스템 켜짐" — 파괴적이지 않음). 수식 안 `**`는 LaTeX에서 등장하지 않는 문자열이라 실질 오탐 없음. CLI가 더 엄밀한 판정(예: 렌더 결과에 strong 존재 여부)으로 대체 가능하면 v2 제안.
- memo: blocks 참조 동일성 기준 useMemo — 타이핑마다 전수 regex 방지(편집 미리보기 사이트).

### 2-4. 인쇄 (D6)

```css
/* PrintStyles.css — 인쇄는 톤 시스템 전체 무효 + key만 굵게 */
.print-body .solution-tone.has-key { color: inherit; }           /* 100% 복원 */
.print-body .solution-tone.has-key strong,
.print-body .solution-tone.has-key .callout-block { color: inherit; font-weight: 700; }
/* KaTeX 가짜 볼드 가드 — 수식은 weight 제외 */
.print-body .solution-tone.has-key strong .katex,
.print-body .solution-tone.has-key .callout-block .katex { font-weight: 400; }
```

- 결과: 인쇄에서 key 문장의 **한글/텍스트만 굵게**, 수식 글리프는 원형 유지. key 안 수식이 인쇄에서 시각적 강조를 잃는 문제는 **미결 Q1**(§7) — v1 기본값은 "수용"(텍스트 굵기만으로 문장 단위 식별 가능 + callout은 들여쓰기 구조가 이미 식별자).
- 화면·인쇄 parity 원칙의 **의도적 예외**임을 CLAUDE.md/roadmap에 1줄 명기(§6).

### 2-5. P3 — 툴바 "핵심문장" 버튼 (D7)

`MarkdownEditorHandle`에 토글 명령 추가:

```ts
toggleKeyWrap(): 'wrapped' | 'unwrapped' | 'rejected'
```

동작 규칙:

1. **선택 없음 → no-op**(rejected). 버튼 tooltip으로 안내.
2. **경계 정돈**: 선택 양끝의 공백을 선택에서 제외(`** text**` CommonMark 불발 방지). 행 끝 `\tag{n}`이 선택에 포함되면 **자동 제외**(tag-marker 행말 정규식이 `**` 뒤에서 깨지는 것 방지 — key와 참조번호는 의미상으로도 분리가 옳다).
3. **문단 제약**: 정돈된 선택 안에 빈 줄(`\n\s*\n`)이 있으면 rejected — 한 문단 내로 강제(덕수 확정). 블록 경계는 에디터가 블록당 1개이므로 자동 충족.
4. **수식 경계 가드**: Phase 56의 `buildMathIndex`를 재사용해, 선택 양끝이 수식 구간 **내부**에 있으면 rejected(`$...$`를 통째로 포함하는 것은 허용). `$$` 구간을 걸치는 선택도 rejected — display 수식은 D8 관행(callout)으로 유도.
5. **토글**: 정돈된 선택이 이미 `**...**`로 정확히 감싸져 있으면(양끝 바깥 2글자 검사 포함) 제거, 아니면 삽입. dispatch는 단일 트랜잭션 — CM 히스토리·Phase 55a 블록 undo에 자연 편입(insertText 선례).
6. rejected 시 사용자 피드백(버튼 흔들림 또는 상태 메시지) — 구현 방식은 CLI 재량.

버튼 위치: MathToolbar 우측에 별도 그룹(수식 템플릿과 성격이 다름을 구분선으로 표시). 라벨 "핵심문장", 단축키는 **⌘B 충돌 확인 후** 결정(⌘B가 블록 분할에 이미 배정되어 있다면 대체 후보 ⌘E — CLI 확인).

### 2-6. P4 — 수식 크기 비율 완화 (D10)

현행: 화면 수식은 `--katex-scale`(Phase 57 문서상 **1.15**)로 본문 대비 확대 렌더. 덕수 판정: 과함 — "살짝 큼"은 유지하되 비율 축소.

```css
/* globals.css — 변수 한 곳만 교체 (셀렉터 좌표 CLI 실측) */
:root { --katex-scale: 1.08; }   /* 1.15 → 출발값 1.08, 실측 튜닝 범위 1.06~1.10 */
```

- **튜닝 방법**: 한글(Pretendard)과 KaTeX 세리프는 같은 font-size에서도 x-height·시각 무게가 달라 숫자만으로 결정 불가. 실문항(HAJI.26FS01.15처럼 인라인 수식이 본문에 섞인 문단)에서 1.06/1.08/1.10 세 값을 나란히 비교해 확정.
- **파급 점검(중요)**: 이 변수 하나에 걸린 기존 보정들이 있다 —
  - Phase 57 P4의 \tag 크기 규칙이 "절대값 필수(1em이면 `--katex-scale` 재승수)"로 설계됨 → 스케일 변경 후에도 절대값 경로가 유지되는지 확인.
  - Phase 56의 수식 세로 중앙 정렬·"세로 큰 수식 행 0.4em 패딩"(globals 328-332 부근) 등 **크기 전제 보정값들의 재검토** — 스케일이 줄면 인라인 수식의 라인박스 침범이 완화되므로 오히려 단순해질 수 있음.
  - `\displaystyle` 자동 주입으로 인라인 수식이 이미 크게 렌더되는 것과의 합성 효과 — 체감 크기는 scale×displaystyle 결과이므로 반드시 인라인 수식 기준으로 튜닝.
- **인쇄 무변경**: `.print-body .katex`는 1em(= 10pt) — 이번 판정("과함")이 화면 기준임을 명시. 인쇄도 과한지 덕수 확인(미결 Q5).
- 전 문항 일괄 시각 변화임을 명시(의도된 변화). 편집창(CodeMirror)은 원문 텍스트라 무관.

### 2-7. P5 — 원문자 크기 완화 (D11)

현행(Phase 57 P5 확정값): `.num-circle { min-width/height 1.35em; line-height 1.28em; font-size 0.86em; vertical-align -0.22em; border 0.08em }` — "실측 튜닝" 표기된 값들. 덕수 판정: 본문 대비 과대.

```css
/* globals.css — .num-circle 비례 축소 (출발값, 실측 튜닝) */
.num-circle {
  min-width: 1.24em; height: 1.24em;   /* 1.35em → */
  line-height: 1.17em;                  /* height - border×2 유지 관계로 연동 재계산 */
  font-size: 0.80em;                    /* 0.86em → */
  vertical-align: -0.19em;              /* 세로 중심 재보정 — 실측 */
  /* border 0.08em·padding·radius 등은 유지 (em 기준이라 자동 축소) */
}
```

- **튜닝 원칙**: 원문자는 "본문 숫자와 같은 계열로 읽히되, 원 테두리 포함 총 높이가 행간(1.8)을 침범하지 않고 본문 대문자 높이를 크게 넘지 않는" 크기. 축소 시 두 자리(⑩~⑮) 가독성 하한 확인 — 숫자가 뭉개지면 하한 도달.
- 적용 지점 3곳 연동: 본문 원문자(marker-circled 내부 포함)·선택지 라벨(ChoicesBlock/PrintableContent — Phase 57 §6.2)·인쇄. **인쇄도 동일 축소**(같은 클래스, em 기준 — 10pt에서 테두리 최소 두께 재확인).
- Phase 57 검증 기준(행간 불침범 / 선택지 3·5등분 baseline / marker-circled 내어쓰기 폭 무변경) 재실행.

### 2-8. P6 — 긴 display 수식 접기/펼치기 (D12, 타당성 검토)

**결론: 구현 가능. 단 소스 분할 방식이 아니라 DOM 레벨 방식이어야 한다.**

두 가지 구현 경로를 비교 검토했다:

- **B안(기각) — 소스 분할**: `$$` 원문을 최상위 `\\` 기준으로 쪼개 첫 행/중간/마지막 행을 별도 KaTeX 호출로 렌더. 기각 사유: `\begin{aligned}`·정렬 문맥이 행 분할로 파괴되고, `\\[1.5em]` 간격 정보 소실, "최상위 `\\`"를 원문에서 파싱하는 것 자체가 중괄호·환경 중첩 추적을 요구하는 취약한 작업.
- **A안(채택) — DOM 레벨**: KaTeX는 display 모드에서 **최상위 `\\`마다 `.newline` 스팬을 방출**하고 행 내용은 `.base` 스팬 시퀀스로 나뉜다(반면 `\begin{cases}` 등 환경 내부 `\\`는 vlist 행으로 렌더되어 `.newline`이 생기지 않음). 따라서 렌더 결과에서 `.katex-html`의 자식을 `.newline` 기준으로 그룹핑하면 **"최상위 행"의 개수와 경계를 파싱 없이 정확히 얻는다** — cases 내부 행은 자동으로 세지 않는 것까지 공짜로 해결된다.

동작 사양:

1. 렌더 후 각 `.katex-display`에 대해 최상위 행 수 산출. **≥4행**이면 접기 대상으로 마킹(hover 시 우상단에 토글 버튼 노출).
2. 접기 실행 시 **첫 행·마지막 행 사이의 모든 행**(해당 `.base` 그룹 + 인접 `.newline`)을 `display:none` 처리하고, 그 자리에 클릭 가능한 합성 행 **"⋯ N행 접힘"**을 삽입(클릭 = 펼치기). 스타일은 dim 톤(P2와 동일 회색) — routine 과정이 접혀 있다는 의미와 일치.
3. **기본 펼침**(덕수 확정). 상태는 비영속 — 컴포넌트 로컬(블록 id + 수식 순번 키의 ref 맵). 편집 미리보기의 재렌더(타이핑)에서 상태 유지가 필요하면 ref 맵 유지, 원문이 바뀐 수식은 펼침으로 리셋.
4. 적용 사이트: **EditorView 미리보기 + ProblemView**(덕수 지정). FolderView·ProblemTabContent·공유뷰 포함 여부는 Q6. **인쇄는 항상 펼침**(정적 출력).

주의·검증 필요(CLI):

- **KaTeX DOM 구조 의존**: `.newline`/`.base` 구조는 KaTeX 내부 구현이다. 현재 고정된 KaTeX 버전에서 1·2·4·6행 수식으로 구조 실측 + 버전 고정 정책 확인. 구조가 다르면 A안 성립 여부 재판정.
- **react-markdown 재렌더 수명주기**: 접기 조작이 DOM 직접 조작이면 React 재렌더에 소실된다. useEffect 후처리로 매 렌더마다 재적용하는 구조(마킹·접힘 상태 재부여)로 설계 — Phase 57의 전처리·후처리 선례와 같은 계열.
- **`\tag`·수식 하이라이트와의 상호작용**: (a) `.tag`의 bottom 보정이 접힘 후 높이에서도 성립하는지, (b) Phase 56 `activeMathId` 하이라이트·클릭 중앙 정렬이 접힌 수식을 목표로 할 때 — **접힌 영역이 목표면 자동 펼침** 후 스크롤이 옳다(v1 제안). 편집 커서가 접힌 행 원문에 들어갈 때도 동일.
- **터치 기기**: hover가 없으므로 접기 대상 수식에 상시 노출되는 소형 버튼(또는 수식 탭)으로 대체 — 반응형 분기.
- 접힘 상태에서 세로 높이 변화 → 스크롤 위치 점프 방지(토글 시 해당 수식이 뷰포트에 남도록 보정 — Phase 56 `fastScrollTo` 재사용 가능).

**공수 판정**: P1~P5 대비 확실히 큰 작업(신규 상호작용 + KaTeX DOM 의존 + Phase 56 연계). v1 권고 — **본 Phase에 타당성 검증(CLI 실측)까지만 포함하고, 구현은 검증 결과에 따라 본 Phase Stage 후반 또는 분리 Phase로 결정**. 분리하더라도 D12 사양은 여기 확정분을 승계.
