## 2. v2 정정 (v3에서 바로잡음)

### 2-1. E0 — v1 저자 자기 정정: "목업에서 가짜 볼드가 보였다"는 관찰은 없었다

v1 논의 과정에서 나(web)는 "목업에서 `**` 안의 인라인 수식이 살짝 두꺼워 보였다"고 주장했으나, **목업도 katex.min.css를 로드했으므로 C6의 `font` shorthand 리셋이 동일하게 작동했고, 가짜 볼드는 목업에서도 발생하지 않았다.** 실관찰이 아니라 "상속되면 그럴 것"이라는 추정을 관찰로 착각한 것이다. C6은 명세·실측 양쪽에서 확정 — D5의 근거 교체("굵기+색 이중 신호 회피")를 그대로 승인한다.

### 2-2. E1 — D2 여백 산술: h2의 em 마진은 h2 font-size 기준이다

v2 §3-1의 "현행 체감 상단 = 1.5em + 1em(h2 marginTop) = **2.5em**"은 오류다. `margin: 1em`은 **해당 요소의 font-size 기준**이므로 h2(1.3em)의 marginTop 1em = 본문 기준 **1.3em**. 정정 수치:

| | 위 체감 | 아래 체감 |
|---|---|---|
| 현행 (h2 1.3em) | 1.5 + 1.3 = **2.8em** | 0.5 × 1.3 = **0.65em** |
| P1 적용 후 (h2 1.08em, margin 1em/0.6em) | 1.5 + 1.08 = **2.58em** | 0.6 × 1.08 = **0.648em** |
| D2 목표 | 2.4em | 0.6em |

세 가지 귀결: ① v2의 "실질 변경은 아래뿐"은 부정확 — **위 여백도 h2 축소에 딸려 2.8 → 2.58em로 저절로 줄어든다**(목표 방향과 일치, 문제없음). ② marginBottom 0.5→0.6em 수정의 실효는 **±0.002em으로 사실상 0** — h2 축소분을 정확히 상쇄해 현행 체감을 유지하는 결과가 된다. 그래도 값 자체의 가독성(0.6em = 의도 문서화)을 위해 **수정은 유지**한다. ③ 체감 아래 0.6em을 정확히 원하면 0.55em로 써야 하나(0.55×1.08≈0.6), 0.048em 차이는 지각 불가 — **0.6em 그대로 확정**. 결론(현행 상단 구조 불가침 + marginBottom 한 줄)은 v2와 동일하고 **산술 기록만 정정**한다.

**결론에 미치는 영향**: A안(토큰 재사용) 채택은 흔들리지 않는다 — A안의 근거는 "신규 색 0, 검증된 토큰, 다크모드 확장성"이지 B안의 결격이 아니다. 달라지는 것은 **B안의 예비 가치**다: `#675F52`는 명암비 여유가 충분하므로, J1(A안이 "충분히 물러나지 않는다" 판정) 시 **주저 없이 승격 가능한 예비안**으로 지위가 올라간다. 단 v2가 지적한 "dim이 두 종류로 보일 위험"(`#5D5647`과의 차이 1.16:1 — v3 재계산)은 유효하므로, B안 승격 시 `--text-secondary` 사용처 전반과의 공존을 육안 확인할 것.

### 2-4. E4 — 사용 가이드 문구 정정 (A안의 실제 현상과 불일치)

v2 §6의 D4' 가이드 문구 *"풀이에 `**`가 하나라도 있으면 그 풀이 전체가 흐려지고"*는 **A안에서 사실이 아니다**. A안의 dim = `--text-secondary` = 현행 본문색이므로, `.problem-content-toned`가 있는 사이트(EditorView·ProblemView·FolderView)에서 **비key 텍스트는 픽셀 단위 무변화**다. 실제 일어나는 일은 "수식이 본문 톤으로 내려앉고, key 구간(텍스트·수식)만 진하게 올라온다"이다. 가이드 문구를 다음으로 교체:

> "풀이에 `**`가 하나라도 있으면 **수식이 본문과 같은 톤으로 정리되고, `**` 구간만 진하게** 표시됩니다. 원치 않으면 `**`를 지우세요."

(공유뷰는 기준선이 달라 현상이 다르다 — 이것이 D14의 근거, §3-1.)

### 2-5. E5 — 제목 색 규칙의 숨은 회귀 (v2가 놓친 것)

v2 CSS의 `.solution-tone.has-key h1,h2,h3 { color: var(--text-primary) }`는 v1 목업의 "제목은 항상 풀 톤" 전제를 그대로 옮긴 것인데, **실코드 전제가 다르다**: EditorPreview의 heading 인라인 style은 색을 지정하지 않으므로 현행 제목은 `.problem-content-toned`의 **`--text-secondary`를 상속**하고 있다(= 현재 제목은 "풀 톤"이 아니다). 따라서 v2 규칙은 **has-key 문서의 제목만 진하게 만들어**, ① 마커 유무에 따라 문서 간 제목 색이 달라지고 ② "진한 것 = key"라는 신호의 단독성을 제목이 침식한다.

**v3 처방(기본안): 이 규칙을 삭제한다.** 제목은 has-key 여부와 무관하게 현행 상속(secondary)을 유지 — P1이 크기·굵기로 이미 제목 위계를 만들므로 톤까지 필요 없고, **풀이 안에서 진한 것은 key뿐**이라는 신호가 가장 순수해진다. 제목을 진하게 올리고 싶다면 has-key 게이트가 아니라 무조건 규칙이어야 하나(전 문항 일괄 변화), v3는 권하지 않는다. → 미결 Q1(§6).

### 2-6. E3 — ⌘⇧B 브라우저 충돌 (주의)

⌘⇧B는 Chrome·Edge의 **북마크바 토글**이다. CodeMirror 핸들러가 포커스 상태에서 `preventDefault`로 가로채면 앱 동작이 우선하지만, 가로채기 실패 시 강조 대신 북마크바가 열리는 당혹스러운 실패 모드가 된다. **T10에 "한글 IME + Chrome/Edge/Safari에서 ⌘⇧B 가로채기 성공" 확인을 명시**하고, 실패 시 대체 후보는 **⌘⇧K**(K = key, 주요 브라우저 무충돌). 채택 자체는 ⌘⇧B 유지(B=bold 연상 가치).

## 3. v3 보강 (신규)

### 3-1. D14 — 공유뷰 톤 기준선 정렬 (v2가 발견하고 처방을 비운 항목)

v2 §3-2 실측: **ProblemTabContent(공유뷰)에는 `.problem-content-toned`가 없다** — 본문·수식이 모두 `--text-primary`로 렌더되어, 같은 문항이 앱과 공유뷰에서 다른 톤 기준선을 갖는다. v2는 "반드시 함께 정리할 것"이라고만 쓰고 처방을 남기지 않았다. 이대로 P2를 얹으면 **has-key 시 공유뷰에서만 본문이 실제로 어두워지는(primary→secondary) 별도 현상**이 생겨, E4에서 정정한 가이드 문구조차 사이트에 따라 참/거짓이 갈린다.

**D14**: Stage 4에서 ProblemTabContent의 콘텐츠 컨테이너에 `.problem-content-toned`(또는 동등 톤 규칙)를 부여해 **5개 사이트의 톤 기준선을 통일**한다. 공유뷰 전 문항의 본문색이 primary→secondary로 일괄 변경되는 의도적 변화이며(Phase 43 위계를 공유뷰에도 적용하는 지연된 정합화), 배포 전 덕수 육안 확인 1건 → 미결 Q2. 공유뷰 카드 배경색이 v2 표에서 **미실측("확인 필요")으로 남아 있으므로** T0에서 실측해 T8 명암비 검증에 포함할 것 — 배경이 `#EDE6DA`보다 어두우면 D3 판정에 영향.

### 3-2. T0 — 좌표 재대조 Stage (Stage 0 신설)

v3는 레포 미접근 환경에서 작성되었고, v2의 좌표(파일:행)는 `f7c4a37` 기준이다. 구현 착수 직전에 **v2 §0 표의 9건 + §3의 좌표 인용 전부를 현행 HEAD와 대조**하는 T0를 Stage 0으로 둔다. 특히: EditorPreview 335-343(heading) · globals 106-108(`--katex-scale`) · globals 26-34(`@font-face`) · UnifiedToolbar 22-42(아이콘 상수) · 5개 사이트 paddingTop 하드코딩 · **공유뷰 카드 배경색(§3-1, v2 미실측 잔여)**. 좌표가 이동했으면 값만 갱신하고 설계는 불변.

### 3-3. 소소한 보강 3건

- **V1 — key 행의 `\tag{n}` 참조번호는 dim으로 남는다**: 툴바가 `\tag`를 자동 제외(§3-3 규칙 2)하므로 key 문장 끝의 tag-marker(색 상속)는 dim 유지. **의도된 동작으로 승인**(참조번호는 routine 메타데이터) — T5에 확인 항목으로 명시.
- **V2 — D8 가이드 예시 표기**: `**$ x = … $**`처럼 `$` 안쪽에 공백을 둔 예시는 remark-math 엣지(공백 스트립 규칙)에 걸릴 수 있으니 가이드 예시는 공백 없는 `**$x=\frac{…}{…}$**`로 통일 표기.
- **V3 — 워크플로우 기록**: roadmap Phase 58 절에 v1(web, 목업·방향) → v2(CLI, 실측 9건 정정·D13 반영) → v3(web, 수치 재계산 정정 E1·E2, 숨은 회귀 E5 적발, D14 보강)을 한 줄씩 남긴다 — Phase 56에서 확립한 교차검증 워크플로우의 두 번째 실행 사례.
